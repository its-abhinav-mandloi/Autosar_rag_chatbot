## 1. Problem Statement & Domain Selection

### Domain
**Automotive Embedded Software — AUTOSAR Basic Software (BSW) Specifications**

### Problem
AUTOSAR (AUTomotive Open System ARchitecture) specifications comprise **10,000+ pages** across dozens of BSW modules (Com, NvM, Dem, Os, CanIf, etc.). Embedded systems engineers routinely need to:

- Look up specific configuration parameters across multiple specification PDFs
- Understand inter-module dependencies (e.g., Com ↔ PduR ↔ CanIf routing)
- Find exact API signatures, behavioral specifications, and requirement IDs
- Cross-reference requirements between AUTOSAR Classic Platform versions

**The manual lookup process takes 15-30 minutes per query** and is error-prone. A single question like *"What is the Com stack configuration for PDU routing?"* may require searching through 5+ documents, each 200+ pages.

### ML-Based Solution
Build a **Retrieval-Augmented Generation (RAG)** system that:
1. Ingests AUTOSAR specification PDFs
2. Parses and chunks them semantically by section headings
3. Creates dense vector embeddings using a neural embedding model
4. Enables natural language querying with **citation-backed answers** generated by a local LLM

## 2. When to Use ML — Justification (M2 Concepts)

| Criterion | Assessment | Justification |
|-----------|-----------|---------------|
| **Is it a prediction task?** | ✅ Yes | Semantic search is fundamentally a relevance scoring/prediction problem — the embedding model predicts similarity between a query and document chunks |
| **Is the data too complex for rules?** | ✅ Yes | Natural language understanding of technical documents cannot be solved with keyword matching or regex alone — it requires learned representations |
| **Is there sufficient data?** | ✅ Yes | AUTOSAR specifications provide 10,000+ pages of structured technical content |
| **Is there a feedback loop?** | ✅ Yes | User thumbs-up/down ratings enable continuous improvement of retrieval quality |
| **Is ML the right investment?** | ✅ Yes | The alternative (manual search) costs 15-30 min/query × hundreds of queries/month = significant engineering time saved |

### Why Not Traditional Search?
- **Keyword search** fails for synonyms ("Com stack" vs "Communication module") and multi-hop reasoning
- **Regex/pattern matching** cannot understand intent or generate coherent answers
- **Full-text indexing** lacks the semantic understanding needed for technical Q&A

## 3. Measurable Goals (GR4ML)

| Goal ID | Metric | Target | Measurement Method | Rationale |
|---------|--------|--------|-------------------|-----------|
| **G1** | Retrieval Precision@5 | ≥ 85% | Manual evaluation on 50 test queries — measure if top-5 retrieved chunks contain the answer | Primary value: correct retrieval drives correct answers |
| **G2** | End-to-End Answer Latency | < 3 seconds (P95) | Automated timing from API logs across 100 queries | Engineers need fast responses during active development |
| **G3** | Hallucination Rate | < 5% | Manual review of 50 answers — flag claims not supported by retrieved context | Safety-critical domain: wrong information could cause vehicle software defects |
| **G4** | Citation Accuracy | ≥ 90% | Verify that cited page/section numbers match the actual source content | Engineers must be able to verify answers against the spec |
| **G5** | Ingestion Throughput | < 5 min per 200-page PDF | Timed ingestion runs | Practical requirement for onboarding new specifications |
| **G6** | System Uptime | ≥ 99% | Heartbeat monitoring over a 7-day period | Engineers rely on the tool daily |

## 4. GR4ML Requirement Specifications

### Functional Requirements

| Req ID | Requirement | Category |
|--------|------------|----------|
| **FR-01** | The system SHALL accept AUTOSAR specification PDFs (up to 50MB) via a REST API endpoint (`POST /ingest/upload`) | Data Ingestion |
| **FR-02** | The system SHALL parse PDFs and extract text, section headings, tables, and AUTOSAR requirement IDs (`[SWS_*]`) | Data Preparation |
| **FR-03** | The system SHALL split extracted text into semantic chunks of configurable size (default 512 tokens) with configurable overlap (default 50 tokens) | Data Preparation |
| **FR-04** | The system SHALL generate dense vector embeddings for each chunk using a local embedding model (nomic-embed-text via Ollama) | Feature Engineering |
| **FR-05** | The system SHALL store embeddings with metadata (document name, page number, section, requirement IDs) in a persistent vector database (ChromaDB) | Storage |
| **FR-06** | The system SHALL accept natural language queries via `POST /query` and return answers with citations, confidence scores, and latency metrics | Inference |
| **FR-07** | The system SHALL perform semantic similarity search (cosine) to retrieve the top-K most relevant chunks for a query | Retrieval |
| **FR-08** | The system SHALL re-rank retrieved chunks using the LLM to improve precision | Retrieval |
| **FR-09** | The system SHALL generate answers using a local LLM (llama3.2 via Ollama) with anti-hallucination guardrails in the prompt | Generation |
| **FR-10** | The system SHALL extract and return source citations (document, page, section) from generated answers | Explainability |
| **FR-11** | The system SHALL accept user feedback (thumbs up/down) via `POST /feedback` and store it for analytics | Feedback Loop |

### Non-Functional Requirements

| Req ID | Requirement | Category |
|--------|------------|----------|
| **NFR-01** | The system SHALL respond to queries within 3 seconds (P95 latency) | Performance |
| **NFR-02** | The system SHALL achieve ≥ 85% retrieval precision@5 for AUTOSAR domain queries | Accuracy |
| **NFR-03** | The system SHALL maintain < 5% hallucination rate (unsupported claims) | Accuracy |
| **NFR-04** | The system SHALL provide health endpoints for all microservices and detect failures within 60 seconds | Availability |
| **NFR-05** | The system SHALL use only local, free, open-source models — no paid API calls | Cost |
| **NFR-06** | The system SHALL log all requests with correlation IDs for cross-service tracing | Observability |
| **NFR-07** | The system SHALL implement retry logic with exponential backoff and circuit breakers for Ollama calls | Reliability |
| **NFR-08** | The system SHALL version prompt templates and track embedding model versions per document | Maintainability |
